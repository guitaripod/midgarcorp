## Architecture Overview

This is an Astro-based static blog with the following key architectural patterns:

### Content Management
- **Blog posts**: Written in MDX format in `src/content/blog/`
- **Content validation**: Zod schemas in `src/content/config.ts` define frontmatter structure
- **Required frontmatter**: `title`, `description`, `pubDate`
- **Optional frontmatter**: `updatedDate`, `image`, `tags`, `draft`, `series`

### Core Features Implementation
- **Bionic Reading**: `src/utils/bionic-reading.ts` - transforms text by bolding first 40% of words
- **Reading Time**: `src/utils/reading-time.ts` - calculates based on word count
- **Table of Contents**: `src/utils/toc.ts` - auto-generates from MDX headings
- **Related Posts**: `src/utils/related-posts.ts` - finds similar posts by tag overlap
- **Search**: Pagefind integration built during post-build process

### Component Architecture
- **Layouts**: `BaseLayout.astro` for pages, `BlogPost.astro` for posts
- **Interactive Features**: Components like `BionicToggle.astro`, `ThemeToggle.astro` use minimal client-side JS
- **Progressive Enhancement**: Features work without JavaScript, enhanced with it

### Build Process
- Static site generation with Astro
- Go-based CLI tool (`ct`) handles pre-build and post-build tasks
- Pre-build: Fetches App Store data, GitHub data, generates OG images (site OG +
  per-app landing OG via `scripts/generate-app-og.js`)
- Post-build: Runs Pagefind for search indexing
- Shiki for syntax highlighting with `github-dark-dimmed` theme
- Tailwind for styling with typography plugin

### Data Freshness (keep the site current automatically)
- `src/data/opensource.json` is regenerated by `ct fetch-github` in a single GitHub GraphQL pass (stars, releases, commit counts, topics). Requires `GITHUB_TOKEN`; without it the existing file is kept untouched. Refresh locally with `GITHUB_TOKEN=$(gh auth token) ./ct fetch-github`.
- Repo curation lives in `internal/github/fetch.go`: included if described + (≥1 release OR ≥2 stars OR ≥40 commits); see `excludeRepos`, `forceIncludeRepos`, `categoryOverrides` to tune what shows and where.
- `src/data/apps.json` is regenerated by `ct fetch-appstore` from the live iTunes lookup API every build — new App Store releases appear automatically. Taglines/colors/features come from `appEnhancements` in `internal/appstore/fetch.go`, keyed by App Store track ID; add an entry when shipping a new app (fallback is a generic tagline). `appEnhancements` can also carry a `Platforms` override (used for `solar-beam`, whose platform the iTunes data misreports).
- `src/data/landing-live.json` is regenerated by `ct fetch-appstore` too (volatile landing facts: version, price, rating, dates) from the **per-app** iTunes lookup — the developer-wide lookup behind apps.json is edge-cached and lags version bumps by days. `src/data/landing.ts` overlays it onto `landing-facts.json` by track id, so landing-page versions never go stale without a commit.
- `ct audit-store` (run on the daily cron via `.github/workflows/test.yml`, and locally) compares committed `landing-facts.json` against the live App Store and fails on structural drift (platform class / category / price) — it's what catches a repositioning like Solar Beam's paid-TV-app → free-Mac-app pivot before a visitor does.
- CI (`.github/workflows/test.yml`) deploys to Cloudflare Pages on push to master AND on a daily cron (plus manual `workflow_dispatch`), so the live site picks up new repos/apps without a commit.
- Pages compute featured selections from the data (latest apps by release date, top CLI tools/OSS by stars) — never hardcode project lists in pages.

### App Landing Pages (`/<slug>`)
- Every App Store app has a marketing landing page at `midgarcorp.cc/<slug>`, rendered by `src/pages/[app].astro` (prerendered static via `getStaticPaths`). Slugs are concatenated brand names (`dreameater`, `psywave`, `solarbeam`, …).
- Data is split into facts (auto, from the stores) and copy (hand-tuned), merged by `src/data/landing.ts` into typed `LandingApp[]` (`landingApps`, `getLandingApp`, `primaryDevice`, `deviceKeys` — the page list is driven by this, never hardcoded):
  - **Facts** — `src/data/landing-facts.json`: real store screenshots (self-hosted webp in `public/screenshots/<slug>/`), price, rating, description, platforms, icon. Generated by `scripts/fetch-store-assets.py` from the App Store Connect API (screenshots, original-res, per device type) + the iTunes lookup (price/rating/description). It is committed; refresh it by running the script locally (`source ~/.config/midgar/credentials.env`), or let CI do it: `.github/workflows/refresh-store-assets.yml` runs `fetch-store-assets.py --live-only` weekly and opens a reviewable PR with the screenshot diff. That workflow is dormant until repo secrets `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_PRIVATE_KEY` (the .p8 contents) are set, and needs the repo setting **Settings → Actions → General → Allow GitHub Actions to create and approve pull requests** enabled. Screenshots still don't refresh on the normal build (only this workflow / a local run pulls them).
  - **Copy** — `src/data/landing/<slug>.json`: hero, features, how-it-works, FAQ, SEO title/description/keywords, screenshot captions, accent color. Authored/refreshed via the `scripts/content-workflow.js` agent workflow (schema lives in `src/data/landing.ts`).
- Components in `src/components/landing/`: `AppStoreBadge`, `StarRating`, `ScreenshotShowcase` (+ `DeviceFrame`), `FeatureGrid`, `FaqAccordion`. Per-app accent color tints decorative elements (darkened for light-mode contrast).
- SEO per page: per-app `<title>`/meta/canonical + per-app OG image (`public/og/<slug>.png`) + `SoftwareApplication` + `AggregateRating` + `BreadcrumbList` + `FAQPage` JSON-LD.
- The price chip comes from `landing-facts.json`. `status: "review"` apps render a "Coming soon" badge instead of a live App Store link. The `/apps` cards link through to these pages (matched by App Store track ID).

### Linux Apps Page (`/linux`)
- `midgarcorp.cc/linux` lists every open-source app/tool the developer ships for Linux — GTK/KDE desktop apps, a Wayland daemon, a tray toggle, and the CLI/TUI bench — as the platform-parallel to the Apple `/apps` page. Rendered by `src/pages/linux.astro`, grouped into **Desktop & daemons** then **Command-line**, and led by the flagship desktop apps.
- **Data** — `src/data/linux-apps.json` is self-contained (name, description, stars, release count, latest version, dates, install commands, binary links) and is the single source of truth; `src/data/linux.ts` reads it directly into typed `LinuxApp[]` (`linuxApps`, `linuxGroups`, `linuxStats`, `featuredLinuxApps`).
- **Generator + auto-discovery** — `scripts/fetch-linux-releases.mjs` **auto-discovers** which apps belong on the page, so new tools appear without editing a list. It starts from the already-curated `opensource.json` (which applies the site's release/stars/commits threshold, `excludeRepos`, and category overrides) and keeps the **Rust/Go/C++ projects that ship releases and aren't SDKs (`SDK_CATEGORIES`) or web apps (`WEB_HOST_RE` — workers.dev/pages.dev/vercel/netlify homepages)**. Everything else is derived or fetched live from GitHub (`gh` CLI) / crates.io / AUR. Maintenance is exception-only, via four small consts at the top:
  - `FORCE_INCLUDE` — repos the rule can't see (`flaccy` is an iOS-primary repo that also ships a Linux desktop app; a brand-new repo not yet in `opensource.json`).
  - `EXCLUDE` — a false positive the rule let through.
  - `OVERRIDES` — correct one auto-derived field (e.g. `image-collage` is tagged `tui` but runs as a CLI; `flaccy` needs a Linux description + `homepageUrl: null` so its card links to the repo, not its iOS landing page).
  - `LEAD` — pin flagship apps (`flaccy`, `emojipick`) to the top.
  - Auto-derivation: `form` (daemon→gui→tui→cli from topics/description), `note` (KDE/Wayland or GTK4), `lang` (from GitHub language), and the crates.io crate (tries `id`, `id-cli`, `id-rs`). Latest version is the **newest across crates.io / AUR / GitHub-release tag**; install priority is **crates.io → Homebrew (auto-discovered `guitaripod/homebrew-*` taps) → AUR (auto-discovered by maintainer) → from source**. Gotchas already handled — don't re-derive: `go install` is omitted (post-rename modules 404 / serve stale majors); crates are accepted only when the crates.io **owner login is `guitaripod`/`marcusziade`** (crate names are a global namespace — `circadia` is taken by an unrelated third party); AUR `pkgrel` suffixes are stripped; a specific-arch release tarball is a "download" link, never the primary install.
- **Freshness / how new apps appear** — `.github/workflows/refresh-linux-apps.yml` runs weekly: it rebuilds `ct` + runs `ct fetch-github` to refresh `opensource.json` in the runner (this is what surfaces a newly-shipped repo to the discovery rule), regenerates `linux-apps.json` + the OG image, then opens a **reviewable PR** with only the Linux data (opensource.json is reset so the PR stays focused). So a new Rust/Go/C++ tool you ship lands on `/linux` on its own — you just review and merge. Needs no secrets (built-in `GITHUB_TOKEN`), but the **Allow GitHub Actions to create … pull requests** repo setting. Refresh locally anytime with `node scripts/fetch-linux-releases.mjs` (uses your `gh` auth). Release counts/stars are a gather-time snapshot, not the daily-build live value.
- **Component/SEO** — `src/components/LinuxAppCard.astro` (terminal card: form glyph, version chip, install block with copy-to-clipboard, alt-channel labels, GTK4/Wayland note, source/docs/releases/download links). Page has a `SoftwareApplication` `CollectionPage` JSON-LD (`operatingSystem: Linux`), per-page OG at `public/og-linux.png` (generated by `scripts/generate-linux-og.js`, wired into `ct prebuild`). Nav (`Header.astro`) and a homepage `~/linux` teaser are driven off `linux.ts`; the nav gates on `lg` (8 items) so md uses the mobile menu.

### Design System ("PHOSPHOR" terminal aesthetic)
- Tokens in `tailwind.config.mjs`: `term.*` (dark: `#0d1117` bg, `#33ff66` phosphor green, `#ffb000` amber) and `paper.*` (light: `#fdf6e3` warm paper, `#073642` ink, `#005f00` green). Use token classes, never raw `blue-*`/`gray-*`.
- Utilities in `src/styles/global.css`: `.term-frame`, `.term-frame-hover`, `.term-label`, `.prompt-line` (renders `$ ` prefix), `.phosphor`, `.cursor-blink`, `.crt-overlay`. Corners are `rounded-sm`/square.
- Safari color-scheme triad must stay in sync when changing canvas colors: `html`/`html.dark` background in global.css, `theme-color` metas in BaseHead.astro, and the inline pre-paint theme script.
- Font: self-hosted JetBrains Mono variable (`public/fonts/jetbrains-mono-var.woff2`); blog prose body falls back to sans via `.prose` rules in global.css.

## Key Patterns

### Adding New Blog Posts
Create `.mdx` files in `src/content/blog/` with proper frontmatter schema validation.

### Adding or Refreshing an App Landing Page
1. Add the app to the `APPS` list in `scripts/fetch-store-assets.py` (slug, trackId, accent color, status), then `source ~/.config/midgar/credentials.env` and run it to fetch screenshots + facts into `landing-facts.json` + `public/screenshots/<slug>/`.
2. Author `src/data/landing/<slug>.json` — run `scripts/content-workflow.js` for that slug, or hand-write to the schema in `src/data/landing.ts`.
3. `node scripts/generate-app-og.js <slug>` to render its OG image.
The page appears automatically once both facts and copy exist for the slug (the route is driven by `landingApps`). When an app's App Store price changes, re-run `fetch-store-assets.py` and redeploy.

### Feature Toggles
Most features can be toggled by removing components from layouts (e.g., removing `<BionicToggle />` disables bionic reading).

### Styling Approach
Uses Tailwind classes throughout components. Global styles in `src/styles/global.css`. Theme customization in `tailwind.config.mjs`.

## Pre-deployment Checklist

**IMPORTANT**: Before pushing code that will trigger a deployment, ALWAYS run these checks:

1. **Code Formatting**: Run `npx prettier --check "src/**/*.{js,ts,astro,css}"` to ensure all code is properly formatted. If it fails, run `npx prettier --write "src/**/*.{js,ts,astro,css}"` to fix formatting issues.

2. **Tests**: Run `npm test` to ensure all tests pass.

3. **Build**: Run `npm run build` to ensure the site builds successfully without errors.

These checks are enforced by GitHub Actions CI and will cause deployment to fail if not passing.
